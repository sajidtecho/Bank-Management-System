Interview & Concept Guide: Bank Management System 🎓

Designed for placement preparation at Cognizant, TCS, Accenture, Wipro, Infosys, and Deloitte.

The 60-Second Project Pitch:
"I built a production-quality Bank Management System in Core Java using a decoupled layered architecture (Controller-Service-Repository pattern). It simulates a banking system with role-based logins (Admin and Customer), transactional security, auto-generated account numbers, and transaction logs. Instead of a database, I implemented a robust, synchronized flat-file database handler using Java File I/O. The project is designed strictly following SOLID principles and core Object-Oriented Programming (OOP) patterns. I used modern Java features like the Streams API, Lambdas, Optionals, and the Java Time API to make the code clean, thread-safe, and highly maintainable."

🏗️ 1. Layered Architecture (De-coupling)

This project is structured into 5 distinct layers to enforce separation of concerns:

  • Presentation Layer (UI): Displays console menus and handles scanner inputs (ConsoleMenu).
  • Controller Layer: Intercepts incoming requests and handles presentation exception mappings (BankController).
  • Service Layer: Validates constraints and executes bank business rules (BankServiceImpl).
  • Repository Layer: Manages read/write connections to files (AccountRepositoryImpl).
  • Storage Layer: Local flat files (accounts.txt, transactions.txt, admins.txt).

🧩 2. Core OOP Principles Applied

A. Encapsulation

Wrapping data (variables) and code (methods) together as a single unit. In our code, in User.java and Account.java, all properties (such as balance, pin, locked) are declared private. They can only be accessed or updated using validated getters and setters.

B. Inheritance

Subclassing parent attributes to reuse code. In our project:

  • User (Abstract class) → Extended by Customer and Admin.
  • Account (Abstract class) → Extended by SavingsAccount and CurrentAccount.

C. Polymorphism

The ability of an object to take on many forms. At runtime, calling the abstract method account.getMinBalance() dynamically executes the correct subclass logic (returning 500.0 for SavingsAccount or 2000.0 for CurrentAccount).

D. Abstraction

Hiding implementation complexity. In our project, layers interact through contracts like the BankService and AccountRepository interfaces without knowing how the underlying data is queried or processed.

⚡ 3. SOLID Principles Implemented

Principle Concept Implementation in our Project
Single Responsibility A class should do exactly one thing. ConsoleMenu handles UI; ValidationUtil checks formats; FileUtil handles streams; BankServiceImpl holds business rules.
Open/Closed Open for extension, closed for modification. To add a new type (e.g., JointAccount), we simply extend Account without modifying the parent class.
Liskov Substitution Subclasses must substitute parent classes cleanly. We pass SavingsAccount and CurrentAccount objects anywhere an Account instance is expected.
Interface Segregation Interfaces should be focused and split. BankService and AccountRepository expose precise methods required by callers.
Dependency Inversion Depend on abstractions, not concretions. BankServiceImpl depends on the interface AccountRepository. This makes it trivial to switch from flat files to a SQL database repository.

☕ 4. Modern Java 8+ Features Used

  • Streams API & Lambdas: Used for clean data query operations (e.g., filtering matches in searchCustomers(query)).
  • Optional Wrapper: Used to indicate missing values safely (e.g., Optional<Customer>) and prevent NullPointerException.
  • Java Time API (LocalDate/LocalDateTime): Used for immutable, thread-safe datetime calculations.
  • Method References: Used to simplify lambda syntax (e.g., User::getName).

💾 5. File Handling & Concurrency

  • Buffered Streams: Uses BufferedReader and BufferedWriter wrapped around FileReader/FileWriter for optimal file character processing.
  • Synchronization: When operations modify balance states, in-memory collections sync instantly to files via repository.saveData().
  • Thread Safety: The generation of account numbers is declared synchronized to prevent race conditions.

❓ 6. Common Interview Questions

Q: Why did you use File Handling instead of a SQL Database?

A: "I chose File Handling to demonstrate my core knowledge of Java I/O streams and custom parsing. However, because the application is decoupled through the AccountRepository interface, we can shift to SQLite or MySQL by writing a new implementation class without changing a single line of business logic."

Q: How did you implement transactional safety during transfers?

A: "The transfer method in BankServiceImpl acts atomically. It validates both accounts exist, verifies available balances, and deducts the sender and credits the receiver together. If any validation fails, an exception is thrown before any files are updated, preventing partial edits."

Q: What is the difference between checked and unchecked exceptions?

A: "Checked exceptions (e.g., InsufficientBalanceException) are verified at compile-time, forcing the developer to handle them using try-catch blocks. Unchecked exceptions (e.g., NullPointerException) happen at runtime and usually represent programming bugs."
